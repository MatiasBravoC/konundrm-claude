## T57: drop everything from the first line that may start code

T57's reviews showed that matching a block's closing fence cannot be made safe without a Markdown
parser: each spec review round found another CommonMark construct (a list marker on an earlier
line, an opener CommonMark reads as paragraph text, a lazy continuation line, an HTML block) where
scrub took a line for a close and CommonMark opened a new block there, so code leaked. The main
session, authorized by the user, changed the rule: `scrub` keeps the notes only up to the first
line that may start code and replaces that line and everything after it with one line,
`[rest omitted: it may contain code]`. A line may start code when, after its indentation and any
list or quote markers, it opens a backtick or tilde fence (a backtick inline span is not an opener
unless the line holds U+2028, U+2029 or another separator only `str.splitlines` breaks at), may
open an HTML block, is indented 4 or more columns past its container, or has a tab before its
content. The sections above describe the earlier rule: their `[code removed]` marker and the
`_opening_fence` function no longer exist.

Residual risks accepted by the main session (no further review round, by decision):

- A UTF-8 byte order mark before a fence on the notes' very first line keeps that block's code
  (markdown-it and commonmark.js read no fence there either, but renderers that skip a leading
  BOM would). It needs a BOM producer and code as the first line.
- Code joined by U+2028 or another separator only `str.splitlines` breaks at stays on one kept
  line with its fence reduced to one backtick: no parser sees a block, but a reader splitting on
  those characters sees the code text. No realistic notes producer emits them.
