## What changed and why

S10 is the feature's last slice. It ships the release (version, changelog, README) and closes the gaps that the whole-feature spec review (Phase 4, step 2) and the T53/T54 handover note found. Its tasks come from three sources, each recorded in an HTML comment under the slice heading:
- **T53 and T54:** moved from S8 by the main session (2026-10-30), so S9 could be integrated while they were written and the changelog would cover S9 too.
- **T77 and T78:** the two gaps of the whole-feature spec review (plan change 4bd69e6, which also updates design.md's `tasks.md` header contract).
- **T79:** the stale "one pull request per slice" wording the T53/T54 handover note found (plan change a65babd).

What changes, by area:
- **The release** (T53, R10.1): `plugin.json` goes to 0.6.0, and `CHANGELOG.md` gets a 0.6.0 entry (Added, Changed, Fixed, Known limitations, Upgrading) naming model and effort per role, the rethinker, partitions built in parallel, slice checkpoints with summaries, design decisions, the feature summary, stacked or single pull requests and improvement notes. A contract test keeps the manifest version equal to the first released changelog entry (skipping `[Unreleased]`) and looks the 0.6.0 entry up by version, not position.
- **The README** (T54, Covers: —): it described the 0.5.0 flow. It now lists each agent's model and effort and the variables that override them, adds the rethinker and the process-reviewer, and has a new "Cómo avanza una feature" section: parallel partitions, rethinks, design decisions, the pause after each slice, the feature summary, the two deliveries and the improvement notes.
- **Decisions approved apart from the pauses** (T77, R5.2, R5.3): `Checkpoints: pre-approved` used to make an open decision take the recommended option too. So a user who pre-approved only the pauses had decisions taken without being asked, and one who pre-approved only the decisions was still stopped.
  - Phase 2 now records a separate `- **Decisions:** ask | pre-approved` line; a missing line reads as `ask`. It defines open decisions as the build's `Status: DECISION` results, not the plan's own `- Decision:` options.
  - Phase 3 takes the recommended option only under `Decisions: pre-approved`. With `Checkpoints: pre-approved` and `Decisions: ask`, an open decision still pauses the task.
  - The writing-plans `tasks.md` template carries the line, and the 0.6.0 changelog's decisions bullet and Upgrading note say the same.
  - The R5.3 rules moved out of `test_pre_approved_checkpoints_do_not_stop`, which keeps only R4.5.
- **Feature worktrees outside the project** (T78, R9.2): Phase 3's intro recommended `claude --worktree` or the desktop app's worktree sessions, which put the worktree under `.claude/worktrees/` inside the checkout, where it shows up in the tree and breaks its gates. It now says `git worktree add ../<repo>-worktrees/<NNN-slug> -b feat/<NNN-slug> <default-branch>`, and why the start point matters.
- **Both deliveries named everywhere** (T79, R2.2): develop-feature's description and its Roles row for pull requests, and opening-pull-requests' description, still named only one pull request per slice, though both skill bodies offer the two deliveries since T34. All three now say "stacked pull requests, one per slice (the default), or a single pull request with every slice"; develop-feature's description is 940 characters, under the 1024 limit. Its test checks only that each place names both deliveries, never what a sentence says about them, the lesson T77 paid for.

How it was built and integrated:
- **T77:** built on branch `claude/p-decisions-t77`, cut from 4bd69e6 (side commit 3bd2c63 → 74fccbc), with the rethinker's report, `evidence/T77-rethink.md`, in the task's commit as Rethink step 3 asks. Before integration, the side session checked with `git merge-tree` that it merged cleanly onto d0edf4a, and the full suite passed on the merged tree (403 tests).
- **Order:** T78 was integrated before T77, out of task order, because it was ready first and depends only on T21. T77 depends on T32 and T53.
- **Integration edits in T77's commit:**
  - Two README sentences: the decisions bullet now names `Decisions: pre-approved`, and the pause bullet says approving the pauses does not approve the decisions.
  - This feature's own `tasks.md` header gets `- **Decisions:** pre-approved`. Without it, T77 would have read the header as `ask` for any remaining open decision.

## Risks and high-risk tasks

- **Risk per task:** T53 low, T54 low, T77 low, T78 low, T79 low
- **High-risk tasks:** none (no mutation run required).
- **Open risks:**
  - **T77's test judges prose with regular expressions.** After the rethink its structural rule reads only which header lines and words a sentence names, but its documented and found limits remain:
    - A correct sentence that relates `Checkpoints: pre-approved` to a decision without naming the `Decisions:` line fails (the fix is to name the line).
    - A wrong sentence that names both lines without "or" is left to the positive rules.
    - Spec review 4 found that a Phase 2 sentence naming only the `Decisions:` line and conditioning it on the pauses (for example "…when the user approved the pauses in advance") passes, though it would contradict the required "approving the pauses does not approve the decisions".
    - No test pins the changelog's Upgrading note.
    - No eval grader reads the `Decisions:` line: `behavior-slice-checkpoint` and `behavior-slice-summary` still grade only `Checkpoints:`.
  - **T78's test** counts "instead of" or "rather than" before `claude --worktree` as a recommendation, because it does not reuse the shared negation pattern.
  - **Two features created at the same time** could take the same NNN number, and so the same `../<repo>-worktrees/<NNN-slug>` folder and `feat/` branch.
  - **README and changelog disagree in places:**
    - The changelog's Upgrading still says to run sessions at `high`, while the README names no level.
    - The README intro still says the user always takes the design decisions, which is now true only without `Decisions: pre-approved`; the feature's closing commit fixes it.

  - **Stacked-only wording outside T79's three places:** develop-feature's Slice checkpoint opens with "Each slice ends in a pull request a person reads" and keeps the summary and notes commits "in that slice's pull request" (`SKILL.md:373`, `:382`, `:391`), and engineering-standards' Definition of Done asks that "each slice's pull request was approved by a person" (`SKILL.md:63`). They hold for the default stacked delivery; with a single pull request the Definition of Done line reads as unmet. T79's spec reviewer found them; they are left for a follow-up.
