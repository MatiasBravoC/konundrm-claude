# Slice S5 summary: each role runs only what it needs

- **Spec:** [requirements.md](../requirements.md) · **Design:** [design.md](../design.md) · **Tasks:** [tasks.md](../tasks.md)
- **Tasks:** T16–T19

## What changed and why

S5 changes what each subagent runs, so the full check runs once per dispatch of the implementer
instead of once per role. The test-writer runs only the tests it wrote or changed, never the
project's check command or the full suite (T16, R2.1). The spec, code and security reviewers rely
on the verification output the orchestrator gives them, never run the check or the full suite, and
run only the test or minimal reproduction a finding needs; their four dispatch prompts, the
whole-feature spec review included, carry a field for that output (T17, R2.2). The finding
verifier runs only the tests or reproductions its finding needs (T18, R2.3). The implementer runs
only the task's test and the tests of the code it changed while it works, and the project's check
once at the end of each dispatch: the full suite runs only inside that check, instead of once on
its own and again inside the check (T19, R2.4). The changes are agent and prompt text; the flow
that fills the new prompt fields (parallel reviews, re-reviews) is rewritten in S6.

## Risks and high-risk tasks

- **Risk per task:** T16 low, T17 low, T18 low, T19 low.
- **High-risk tasks:** none.
- **Open risks:**
  - The contract tests match keywords per sentence, not meaning (the plan's convention): a sentence
    with the right words that says the opposite would pass. The reviews read each rule's wording.
  - The prompt label "(verify command, 5 runs)" is not always true: a `chore` task runs its verify
    command once, and after a fix round develop-feature 0.6.0 repeats steps 3–4 without step 2's
    five runs, so the reviewers could get output from before the fix. Before S5 the spec reviewer
    reran the verify command itself. The gate's full check still catches a broken test; S6 (T20,
    T21) rewrites steps 3–4 and should say the orchestrator reruns the verify command after each
    fix round.
  - The implementer's step 6 says to run the check once and fix what it reports, but not to run it
    again after those fixes. The gate's check (and, from S7, `status` before it) catches a report of
    green on a tree that was not checked.
  - fix-bug and reviewing-pull-requests dispatch these agents without verification output; the
    agents' fallback (run only the tests that cover the change) is not pinned by a test.
  - The test-driven-development skill, which the test-writer loads, still says that when resumed it
    runs "the suite so far"; the agent's rule now says never the full suite, and the skill is
    outside S5's files.

## Decisions

- No subagent returned `Status: DECISION`. These choices were made inside the tasks:
- Where each rule lives (T16–T19): `## Process` | `## Rules` → **`## Rules`** for the test-writer,
  reviewers and finding verifier, where their other "never" rules live; **`## Process`** for the
  implementer, whose steps 4–6 are the ones that ran the suite (test-writers, as the orchestrator
  suggested).
- The whole-feature spec review (T17): leave its prompt as is | give it the Phase 4 check output →
  **give it the output** (orchestrator in the red step), since it would otherwise rerun things
  itself.
- A reviewer dispatched without verification output (T17): no rule | run only the tests that cover
  the change → **run only those tests** (implementer), for fix-bug, reviewing-pull-requests and
  direct use.
- R2.3's parts (T18): pin "never the full suite" too | only the criterion's two parts →
  **the criterion's two parts** (orchestrator); the agent's text still says never the full suite,
  in the reviewers' words.
- A step that still runs the suite (T19): pin the rule only | also fail any sentence that runs a
  suite without the check → **also fail it** (orchestrator in the red step), so the old step 4
  could not stay beside the new rule.
- Where the implementer's check runs (T19): at the end of its dispatch | deferred to the gate →
  **the end of its dispatch** (design.md, Data flow step 3); the gate's side is S7's T24.
