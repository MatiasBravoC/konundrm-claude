# Slice S3 summary: `task_ledger.py status` tells where a feature stands in one call

- **Spec:** [requirements.md](../requirements.md) · **Design:** [design.md](../design.md) · **Tasks:** [tasks.md](../tasks.md)
- **Tasks:** T8–T10

## What changed and why

S3 adds the first subcommand of the task ledger, `task_ledger.py status <tasks.md>`, which answers
in one call what the orchestrator used to ask Git piece by piece (R4.1): the plan's base, the tasks
with a commit after it, the next task, whether the tree is clean and whether the check passed for
this exact tree (T8). A task counts as built by its commit after the base, whatever its box says,
so a resumed session starts at the first task without one (R1.8). While a slice's partitions run in
parallel, `status` names each partition's next task in the wave in progress; that logic moved from
the session doctor into `tasks_document.next_tasks`, which both now share (T9). A plan that cannot
be read, has no usable base or names a base Git cannot find ends with exit 2 and `<file>:<line>`
on stderr, changing nothing (T10, R4.6). The flow does not call `status` yet: slice S7 makes
develop-feature use it at the gate and on resume.

## Risks and high-risk tasks

- **Risk per task:** T8 low, T9 low, T10 low.
- **High-risk tasks:** none.
- **Open risks:**
  - T10 changed how the plan reader drops HTML comments: a comment now leaves its line breaks
    behind, so the reported line number matches the file. A comment that spans lines inside a task
    line or a partition-table row would now split that line instead of rejoining it. No real plan
    has one: the old and new readers give identical results on feature 001's plan (79 tasks), this
    plan and writing-plans' template. No unit test pins the comment rule, that only the first
    `Base commit:` line is read, or `is_readable`; reverting the comment rule would leave every test
    green.
  - Every `GitError` is reported as "base commit X is not in this repository", also when Git
    itself is missing; exit 2 is right either way.
  - `status` compares the plan's task IDs as written with the unpadded IDs `task_commits` returns,
    so a plan that zero-pads its IDs (`**T01**`) shows no task as committed and names T01 as next
    even after a `Task: T01` commit (reproduced in a scratch repository). Plans from writing-plans'
    template do not pad; S4's `message` and `close-slice` will meet the same key.
  - `status` answered in 0.55 s on this 42-task plan; the 100-task bound of the constraints is
    measured in the Phase 4 diagnosis.

## Decisions

- No subagent returned `Status: DECISION`. These choices were made inside the tasks:
- How `status` writes its output (T8): the locale's code page | UTF-8 whatever the locale →
  **UTF-8** (orchestrator in the red step), since the plan's titles carry accents and the plugin's
  other CLIs already switch stdout to UTF-8.
- What "clean" means (T8): `git status --porcelain` | the content snapshot equals HEAD's tree →
  **the snapshot** (implementer), reusing the snapshot the check line needs.
- The next line while partitions run in parallel (T9): a `next:` line plus a per-partition line |
  a `next per partition:` line in its place → **in its place**, with the session doctor's wording
  (orchestrator's suggestion to the test-writer), since a `next:` naming one task would mislead a
  partition session.
- Which line a missing `Base commit` line is reported at (T10): line 1 | where the template puts
  it → **line 1** (orchestrator in the red step).
- Where the `Base commit` line's number is kept (T10): a second pattern in `task_ledger.py` |
  `TasksDocument.base_commit_line` → **`tasks_document`** (orchestrator), the single reader of
  tasks.md; `read_tasks` still never raises, so an unreadable file is `is_readable=False`.
- A base Git cannot find (T10): leave the traceback (exit 1) | exit 2 at the `Base commit` line →
  **exit 2** (orchestrator, from T8's code review), since exit 1 means "refused".
