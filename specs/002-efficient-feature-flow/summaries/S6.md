# Slice S6 summary: a task's reviews run at once, share one fix round and pass on its final code

- **Spec:** [requirements.md](../requirements.md) · **Design:** [design.md](../design.md) · **Tasks:** [tasks.md](../tasks.md)
- **Tasks:** T20–T23

## What changed and why

develop-feature's task loop now launches the spec and code reviews at the same time, in one
message, each with the orchestrator's verification output, and on high-risk tasks the security
review with them instead of after a clean code review; only the writers (test-writer, implementer)
still run one at a time, never while a reviewer runs, and the audit hook's docstring says why
reviewers may overlap (T20, R3.1, R3.5). Every finding of that batch goes to a single fix round,
after which the orchestrator reruns the verify command and runs the reviews again at once with a new
re-review prompt: each review gets its previous findings, the fix round's reports and the new
verification output, and rereads those files instead of the whole task (T21, R3.2, R3.3). A task is
committed only when its reviews passed on its final code: a change made while verifying by risk or
after a red check goes back through the reviews (T22, R3.4). The audit already restores a
reviewer's change whichever concurrent reviewer stops first; T23 pins that with tests and no code
change (R3.6). The reviewer prompts' label "(verify command, 5 runs)", an open risk of S5, now
reads "5 runs, or 1 for a `chore` task".

## Risks and high-risk tasks

- **Risk per task:** T20 low, T21 low, T22 low, T23 medium.
- **High-risk tasks:** none. T23 (medium): nine hand mutants of `audit_subagent_changes.py`, run
  in a copy of the hooks folder against `ConcurrentReviewersTest` (never restores; restores
  without blocking; two blocks before the restore; the restore leaves the record; a clean stop
  leaves the record; created files not removed; restore to the current tree; one shared record per
  session; a clean stop drops every agent's record) → 9/9 killed.
- **Open risks:**
  - A reviewer that starts after another reviewer's change, while that one still runs, would put
    the change back at its own stop, since its snapshot holds it (checked by hand; outside R3.6,
    not tested). develop-feature launches a batch's reviews in one message, so every snapshot comes
    before any change; a flow that starts reviewers at different times would hit it.
  - When another reviewer stops first, the hook blocks that reviewer and its warning names that
    role for a change it did not make; the change is restored either way.
  - Step 6 (gate): after a red check the fix goes back through the verify command and the reviews,
    but the text does not say whether step 5 (verify by risk) runs again, so on a `high` task a fix
    at the gate could leave the mutation run and the end-to-end evidence stale. S7 (T24) rewrites
    the gate.
  - The `## re-review` prompt's "keep its lines up to the task's criteria or Security line" has no
    cut point for the code-reviewer prompt, which has neither; the fix round's reports are the
    writers' own claims (Decision A's known cost; Phase 4's whole-feature spec review catches what
    escapes).
  - `agents/security-reviewer.md` still says it is dispatched "after the code review" (`:3`) and
    opens with "A code reviewer already judged design and readability" (`:10`); develop-feature now
    dispatches it with the code review. Outside this slice's files.
  - The contract tests match keywords per sentence or block, not meaning (the plan's convention).
    Known gaps: the bare word "writers" exempts a "subagents one at a time" sentence (T20); `code`
    exempts a re-review sentence about added tests only (T22).
  - T22's implementer ran the check piped (`npm run check 2>&1 | tail -25`), which the plugin does
    not record, so the gate ran it again; its dispatch prompt asked for the check alone, but the
    implementer agent's own text does not say so.

## Decisions

- What a re-review receives as "what changed" (T21, chosen at plan approval): its previous findings
  and the fix round's report, rereading those files | its previous findings and a `git diff`
  against a snapshot taken before the fix → **the fix round's report** (user).
- No subagent returned `Status: DECISION`. These choices were made inside the tasks:
- Step numbers (T20, T21): renumber | keep 3 and 4 → **keep them** (implementer), so every
  reference holds: step 3 is the batch of reviews, step 4 its single fix round; Parallel
  partitions step 6 now points to step 4, where the routing moved.
- Which reviews run again after the fix round (T21): those with findings | the whole batch →
  **the whole batch, at once, with the re-review prompt** (orchestrator), so every review passes on
  the final code; a review that passed gets "none" as its previous findings.
- Where the commit condition lives (T22): the end of step 4 | step 7 → **step 7** (implementer).
- T23's scope (orchestrator): reviewers started before the change, as the invariant says; late
  starters, tool artifacts and linked worktrees left out.
