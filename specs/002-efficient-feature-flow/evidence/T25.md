Covers R2.7, R4.2, R4.3 · Threats row 2 of `design.md` (orchestrator → `git commit`).

## End-to-end run of the real commit gate

A throwaway script in the session scratchpad (`t25_e2e.py`, kept in the session notes folder as
`s7-tools/t25_e2e.py`) builds a Git repository outside the project with a plan
(`specs/001-demo/tasks.md`: base commit, tasks T1 and T2, boxes open). It then plays the flow of
develop-feature's steps 6 and 7 with the real hooks, each event sent through
`sh plugins/konundrm-eng/hooks/run.sh <script>` the way Claude Code sends it:

1. The implementer's last check: the check runs once, then its PostToolUse event (with
   `agent_type: konundrm-eng:implementer`) goes to `record_check_result.py`, which records the
   tree's fingerprint for the session and beside the repository.
2. The gate: `task_ledger.py status` shows the check green, so the orchestrator sends the commit
   line exactly as step 7 writes it. Its PreToolUse event goes to `gate_git_commit.py`; once the
   gate allows it, the script runs the line itself, as Claude Code would.
3. A red check: T2's change with the check failing and no green check recorded for that tree.
4. The same commit line sent by a subagent.

The check is a one-file script outside the repository (set through `KONUNDRM_CHECK_CMD`) that
logs every run, so the output shows whether the gate ran it. T25 changes no hook: the run uses
this tree's `run.sh` and hook scripts. Run on Windows 11 (Git Bash), 2026-10-31.

Command, from the repository root:

```
python -I "$SCRATCHPAD/t25_e2e.py" plugins/konundrm-eng/hooks/run.sh "$SCRATCHPAD/t25-work"
```

## What it shows

- **Red check, denied (R4.3).** With no green check for T2's tree, the gate runs the check (the
  log goes from 1 to 2 runs), gets exit 1 and denies the command, so HEAD does not move.
- **Green with the implementer's fingerprint, committed without a second check (R4.3, R2.5).**
  The gate finds the green result the implementer's check left for this exact tree and lets the
  line run: the log stays at 1 run before the gate, after it and after the commit.
- **One call, its message from `message` (R4.2, R2.7).** The commit's message is the subject and
  the trailer block `Task: T1 · Covers: R1.1`, `Rounds: spec 1 · code 1 · escalations 0` and the
  session's `Co-Authored-By`, all three read by Git as trailers (`%(trailers:only)`). The commit
  holds only the task's file: the plan is not in it, and T1's box is still open (R2.7). `status`
  counts T1 as committed from the commit alone.
- **Only the orchestrator commits.** The same line from a subagent is denied before any check.

## Invariant and mutation

- Invariant ("ningún paso del flujo commitea fuera de un `git commit` visible en la línea de
  comandos"): `test_task_ledger.py::MessageTest::test_message_never_commits_or_changes_the_repository_whatever_its_input`
  calls `write_task_message` in process with 16 seeded inputs (planned, zero-padded, committed and
  unknown task IDs; subjects and bodies with shell metacharacters, newlines and non-ASCII; valid
  and arbitrary rounds). After each call every file of the repository, working tree and `.git`,
  is byte for byte as before, except the message file when the call succeeds; a refusal changes
  nothing. No commit, ref, index or object change can come from `message`. Five runs in a row
  pass in 1.75–1.90 s each.
- Mutation: the task's changes are prose (`Mutation: no aplica a prosa`); this run and the
  contract test `test_flows.py::GateFlowTest::test_task_commit_goes_through_the_gate_with_its_message`
  stand in for it.
