# Slice S2 summary: publish a feature live, one stacked pull request per slice in merge order, and pull request text anyone can read

- **Spec:** [requirements.md](../requirements.md) · **Design:** [design.md](../design.md) · **Tasks:** [tasks.md](../tasks.md)
- **Tasks:** T7–T10

## What changed and why

Slices are now planned at 300–500 changed lines of code and tests, with the feature's documents not
counted and 500 as the default budget everywhere, and each slice pause reports both counts and
warns by how much a slice went over (R7.1–R7.4). develop-feature can publish a feature on GitHub
while it is built: at plan approval it checks the remote and `gh`, asks a separate question and
records `Publish: live` or `local`; in live mode each slice gets its own branch, pushed when the
slice starts, every flow commit is pushed as soon as it is made, a resumed session pushes what is
pending, a failed push stops with `BLOCKED:`, nothing is force-pushed and only the main session
pushes (R1.1–R3.6). Each finished slice opens its pull request at once, stacked on the previous
one, with `(k/N)` in the title and a `Merge order:` first line, and the end-of-feature delivery of
a local build stacks the same way (R4.1–R4.9). The pull request text follows the repository's
template or four fixed sections, in plain English and without the flow's IDs, lines or role names,
and the plugin ships as 0.8.0 (R5.1–R5.4, R9.2). This answers the user's ask to follow each feature
on GitHub as it is built, and to have pull requests another developer understands without knowing
the workflow.

## Risks and high-risk tasks

- **Risk per task:** T7 low, T8 medium, T9 medium, T10 medium
- **High-risk tasks:** none
- **Open risks:** suggestions not applied, all non-blocking:
  - A pull request opened live is told to link `summary.md` at the final commit's SHA, which does
    not exist yet when the earlier slices' pull requests open; an older test (`_delivery_link_gaps`
    in `contract/test_flows.py`) forbids making that link conditional, so fixing it needs a plan
    change (`opening-pull-requests/SKILL.md:143-147`).
  - `engineering-standards/SKILL.md:140` still says a pull request description traces each
    requirement to its test and states each task's risk, which the new text rules no longer do.
  - opening-pull-requests step 2 measures the budget with `git diff --shortstat <base>...HEAD`,
    counting the feature's documents, so a slice inside its budget can look over it there
    (`opening-pull-requests/SKILL.md:39-45`).
  - In live mode, the commits a slice checkpoint makes after the summary (improvement notes that
    fell back to the feature folder, the one-session switch) are pushed to that slice's branch and
    join the pull request just opened, not the next one; the Live publishing paragraph also calls
    "the tip of the previous slice's branch" "the commit that adds its summary"
    (`develop-feature/SKILL.md:208-222`).
  - The Live pull request paragraph defers to opening-pull-requests steps 3–5, which wait for a yes
    and may open a draft; the live text overrides both but does not say so
    (`develop-feature/SKILL.md:522-529`).
  - After a fallback to the default branch, `Merge #<n> first.` names a pull request that is
    already merged (`opening-pull-requests/SKILL.md:126-129`).
  - The fix-bug and summary mappings name the four fixed sections, not a repository template's
    matching ones, and setup-project's template lacks the fixed sections' mutation-score hint.
  - Some contract-test rules accept loose keywords (R2.1, R3.2, and R5.4's leave-out patterns), so
    weaker wording would still pass.
